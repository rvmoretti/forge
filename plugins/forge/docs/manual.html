Forge — how you use it

You describe what should exist, at product level. Forge — the main agent operating as your CTO — runs your METHOD to spec it, turns the plan into an enforced work graph, briefs cheaper worker agents, machine-verifies every result, and loops until acceptance criteria pass. The gates are code (a state CLI plus hooks), not promises: DONE requires a passing verification record, no item starts without criteria, a third identical retry is refused, and a session can't end with silently dangling work. All state lives on disk — close the laptop anytime; any new session resumes from forge status.

YOU product owner — decides WHAT FORGE CTO / main agent — decides HOW TEAM worker agents: explorer (haiku) · implementer, tester (sonnet) · reviewer, architect (opus) GATE enforced by the forge CLI + hooks — can't be skipped

📖 The manual

Setup, daily use, and troubleshooting. The full project walkthroughs are the two journeys below — steps tagged YOU are yours; steps tagged AUTO happen on their own. Everything works in plain language; slash commands are shortcuts, never requirements. Prerequisites: Claude Code installed and logged in, git. Node comes with Claude Code.

0 · One-time setup (once per machine, ~5 minutes)

The plugin activates in every Claude Code session after this — nothing to repeat per project.

  1. Get the plugin repo. YOU You received the forge-plugin folder (or zip). Push it to a git repo your team can reach — or use the shared URL if someone already did.
  2. Install it in Claude Code. YOU In any Claude Code session: /plugin marketplace add <repo-url> /plugin install forge@forge-marketplace
  3. Verify. YOU Start a new session (claude). You should see the Forge operating contract load at session start, and /forge:status should respond. If hooks seem silent, check /hooks in Claude Code.
  4. Recommended extras. YOU Install Graphify (deterministic code graph — makes orientation and scoping near-free): uv tool install graphifyy # or: pipx install graphifyy graphify install For web projects, keep Playwright as a dev dependency so E2E criteria can be machine-verified. Skipping either is fine — preflight detects what's missing and asks you once (install, or proceed without); your answer is remembered per project.

C · Every day after

The disk is the memory; sessions are disposable.

  • Resume: open claude in the project and say "continue". The session-start hook loads the operating contract plus a live state digest — no re-explaining, ever.
  • Check: ask "where are we?" — or /forge:status. Phase, work counts, in-progress, blocked, latest discovery.
  • Pause: just say stop. The stop gate makes Forge settle every open item first: done, blocked-with-reason, or failed-with-diagnosis. Nothing dangles silently.
  • New machine or teammate: clone the project repo (state travels in git), do the one-time plugin install, open claude. Same picture, same rules.

D · When something feels off

The usual fixes, in order of likelihood.

  • First move, always: forge doctor (install/state self-check: versions, cache, hooks, locks, orphaned work) and forge trace --refusals (the flight recorder — every CLI call and hook decision, version-stamped). Diagnose before working around anything.
  • A skill didn't trigger? Name it: "run the forge method" / "use forge-brownfield".
  • Hooks not firing? Run /hooks to inspect; after a Claude Code update, reinstall or update the plugin. Hook config formats occasionally shift between releases.
  • Session got bounced at the end? That's the stop gate working — items were still IN_PROGRESS. Let Forge settle them; it happens at most once per stop.
  • Told "state files are managed by the forge CLI"? Also by design — work state changes only through forge task … commands, never hand-edits.
  • Forge's behavior needs tuning? Edit core/OPERATING.md in the plugin — it's deliberately ~130 lines so process changes land in one reviewable place. The full design rationale lives in docs/TRACEABILITY.md.

E · The safety nets (all enforced in code — added v0.5–v0.10)

  • One orchestrator per project. A session lock (heartbeat on every write) blocks a second session's edits while the first is active — no more edit wars. Dead session? forge session takeover --force. Status: forge session status.
  • Scope is enforced. While an item is in progress, edits to its forbidden paths are refused by the hook; options.protect freezes paths always (generated code, migrations).
  • Security is part of the gate. Set verify.security (e.g. gitleaks) and it runs inside every verification; milestone approve refuses until a fresh-context security review of the slice is recorded (forge milestone security <M> --note) — skips are explicit and logged.
  • The spec stays true. Every completed item that touched product behavior updates the spec layers in the same close, on every project — the spec is the source your docs generate from.
  • Screens are designed, not defaulted. Mocks live in spec/mocks/ as approved intent; screen items carry a mock-fidelity criterion, screenshots attach to evidence (task verify --artifact), and a fresh-context UX review judges against the design-ux checklist.

Your input

Natural language.

No prompts, no model picking, no agent wrangling. You talk product. Slash commands (/forge:build, /forge:status, /forge:preflight, /forge:dashboard, /forge:usage, /forge:stats) are shortcuts — plain words always work too.

The only three reasons you get interrupted

1 · Product decision — a spec hole was found; answered as an either/or, recorded to the decisions log 2 · Approval gate — a high-risk operation needs your sign-off 3 · Milestone review — something works end-to-end; try it, redirect

Your output

Ask "where are we?" — or /forge:status

Phase, preflight, work graph counts, in-progress and blocked items, latest discovery. For the visual picture open forge/dashboard.html in a browser — progress, the work graph, and the project map (one box per component: route, progress, mock/screenshot) — regenerated on every state change, zero tokens, just reload. /forge:usage = observed token/dispatch telemetry; /forge:stats = process health (first-pass rate, retries, elapsed times).

From idea to verified product

You

Create the project, open Claude Code, say what you want

The session-start hook has already loaded the operating contract. The spec skill triggers on its own — if it doesn't, say "run the forge method" — and forge init creates the project state. AUTO

2
Forge

Runs the METHOD interview, layer by layer

Vision → Domain → Experience → API → Logic → Foundation — METHOD.md verbatim, shipped inside the plugin. You answer either/or questions one at a time and approve each layer's gate; you never write spec documents yourself. Confirmed decisions land in decisions.md; nothing reaches a deliverable file before you confirm it. YOU

3
Gate

Spec gates → the work graph is born

AUTO At METHOD Step 7, alongside CLAUDE.md and PLAN.md, Forge sets the verify commands (forge config set verify.test …), flips phase build, and converts PLAN.md into work items — each with acceptance criteria carrying a machine check. For products with a UI it also offers the drawn-frontend path: a mock per key screen (Claude Design, Figma export, or a photographed sketch) approved by you into spec/mocks/ — screens with mocks get a mock-fidelity criterion. Then preflight runs (yours to trigger anytime: say "run preflight" or /forge:preflight); if Graphify isn't installed it asks you once — install, or proceed without — and remembers your answer.

Team + Gates

The build loop runs — mostly without you

Brief → worker → forge task verify → review → done or fail-with-diagnosis. Item after item, in dependency order. Check progress anytime — ask "where are we?" or /forge:status — and walk away whenever you like: state lives on disk.

🏗️ Brownfield — existing codebase v0: serviceable

From "add this feature" to a baseline-guarded, verified change

1
You

Open the repo, ask for the change

cd existing-repo && claude you: "Add CSV export to the reports page."

The brownfield skill triggers on its own — if it doesn't, say "use forge-brownfield" — and forge init creates state if it's the first time. AUTO

2
Team

Orientation — Graphify first, Explorer second

Structural questions (entry points, dependency closure of what will change) go to the code graph for ~zero tokens; a haiku Explorer reads only what the graph can't answer, reporting OBSERVED vs INFERRED vs UNKNOWN. No full-repo archaeology for a bounded change.

3
Gate

Verify commands confirmed, baseline captured — before any change

Forge finds the project's real test/lint/typecheck commands (package.json, CI config) and asks you to confirm them YOU — they become the verification gate. Then AUTO forge baseline capture runs them and records the result: RED items are logged as pre-existing — new work must not worsen them and isn't obliged to fix them (say if you want follow-up items). A project with no runnable checks gets told so plainly: the first work items build the harness.

4
Forge

Asks you only what the code can't answer

forge: "Export all rows or respect current filters? All roles or admins only?"

A scoped mini-spec: acceptance criteria with machine checks, work items whose allowed-files scope is derived from the dependency closure.

5
Team + Gates

The same build loop — plus the baseline guard

Verification includes forge baseline check: a regression against the baseline fails the item even if its own criteria pass.

↳ see "The build loop" below

6
Forge

Surprises become discoveries, not detours

"Reports has an undocumented Stripe dependency" → forge discovery add with evidence and impact → work graph updated, or escalated to you if it touches what users experience.

7
You

Receive the finished change

forge: "Done. 6 files, 9 new tests passing, baseline unchanged, docs updated. Export respects filters, admins only — as you decided."

⚙️ The build loop — what runs while you're away

Per work item. The gray gates are the forge CLI — the orchestrator couldn't skip them if it drifted: state files are hook-protected, and every transition below is checked in code. Top-tier tokens go to thinking (briefs, reviews, decisions); the team's cheap tokens go to typing.

1 · Start + brief

forge task start (refused without criteria or with unmet deps) → forge brief skeleton + spec excerpts, decisions, domain pack, Graphify-derived scope.

→
2 · Worker executes

Cheap model, fresh context, bounded task. Stops and reports on any spec hole or scope conflict — never invents, never expands scope.

→
3 · Machine verification

forge task verify runs project checks (incl. verify.security) + criterion checks + the baseline guard, records real output as evidence — screenshots attach via --artifact. The worker's "it works" counts for nothing.

→
4 · Review evidence

Diff + test output + report. High-risk diffs go to a fresh-context opus reviewer (the author's own read is biased); screens get the UX review against the approved mock. Deep code reads only where evidence is ambiguous.

→
5 · Done — proven

forge task done — refused without a passing verification record for the current tree. Spec + docs synced in the same close, next item picked up.

On failure

forge task fail --note "diagnosis" — the diagnosis is required thinking, and it rides into the next brief. Retry = fresh worker, never the failed context. After 2 failures the CLI refuses to start again without --escalate stronger-model | decompose | self. Spec hole found: the loop stops guessing and brings you an either/or. And if a session tries to end with work still IN_PROGRESS, the stop gate bounces it once: done, blocked-with-reason, or failed-with-diagnosis — nothing dangles silently.

What you stop doing

  • Writing and tuning implementation prompts — briefs are Forge's job now
  • Choosing agents and models per task — tiers live in the agent definitions
  • Checking whether the agent really ran the tests — the CLI ran them and kept the output
  • Re-explaining the project after every session — state loads at session start
  • Babysitting retries that repeat the same mistake — the third one is refused

What you keep owning

  • What the product is and who it serves — the spec stays the source of intent
  • Every user-visible behavior decision, recorded with your authority in decisions.md
  • Approvals on destructive / high-risk operations
  • Milestone judgment: "this is right — continue" or "change course"
  • The METHOD — it runs verbatim inside the plugin, unmodified

State on disk, always: forge/config.json (phase, verify commands, options), forge/state/ (work graph, preflight, baseline, session lock, components, trace — hook-protected, CLI-only), forge/decisions.md and forge/discoveries.md (append-only, titled), forge/dashboard.html (generated projection). All plain JSON/markdown, git-versioned. See docs/architecture.html for the functional diagrams and docs/TRACEABILITY.md for the spec-to-implementation map.
