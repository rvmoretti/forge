Forge Companion

Forge turns one Claude Code session into an engineering organization that builds your product while you keep every product decision. This is the day-to-day companion: what to do, what to expect, and what every message means. The deeper "why and how it works" lives in the collapsible panels — open them when curious, skip them when working.

YOU product owner — decides WHAT & WHY FORGE the CTO — decides HOW TEAM worker agents on cheaper models GATE enforced in code — cannot be skipped

What is Forge?

You describe a product in plain language. Forge interviews you until the idea is precise, writes the specification, breaks it into work items, sends each item to a cheaper worker agent, machine-verifies every result (it runs the tests itself — a worker saying "done" counts for nothing), and stops at each milestone so you can try the running product and steer. You are interrupted for exactly three things; everything else happens without you.

1 · A product decisionThe spec has a hole ("should deleting a group keep its expenses?"). You get an either/or with a recommendation. Your answer is recorded forever.
2 · A high-risk approvalSomething destructive or sensitive needs your explicit yes before it runs.
3 · A milestone reviewA working slice is ready. You try it in your browser, say what's right and wrong, and approve the gate — nothing later starts until you do.
How it works under the hood (the one idea)

Forge splits the organization across two substrates. Judgment lives in the model: the main Claude session operates as CTO under an operating contract loaded at every session start — it runs the spec method, writes worker briefs, reviews results, decides how. Enforcement lives in code: a small CLI owns every state change and refuses the moves that historically go wrong — completing work without passing evidence, retrying the same failure a third time, starting the next milestone before you approved the last, two sessions editing the same project at once. The model can drift; the gates cannot.

Everything recoverable lives in plain files under forge/ in your project, versioned in git. The conversation is never the memory — close every window, restart your machine, and the next session picks up exactly where things stood.

What you stop doing, what you keep owning

You stop: writing implementation prompts, picking models per task, checking whether the AI really ran the tests (the CLI ran them and kept the output), re-explaining the project every session, and babysitting retries — a third identical attempt is refused by code.

You keep: what the product is and who it serves, every user-visible behavior decision (recorded with your name in forge/decisions.md), approvals on risky operations, and milestone judgment — "this is right, continue" or "change course".

Install & one-time setup

Once per machine, ~5 minutes. After this, Forge is available to any project you choose to enable it in.

1Prerequisites

Claude Code installed and logged in, and git. That's all — Node comes with Claude Code.

Never used a terminal? Read this first

The terminal is a text window where you type commands. On macOS open Terminal (⌘-space, type "terminal"). Commands in this manual appear in boxes with a Copy button — click it, paste into the terminal, press Enter. cd some/folder means "go into that folder"; everything else is one command per line. You cannot break anything by typing a command wrong — you'll just get an error message you can paste back to Claude.

2Add the Forge marketplace and install the plugin

Open a Claude Code session anywhere (claude in a terminal) and run:

/plugin marketplace add <your-forge-repo-url> /plugin install forge@forge-marketplace --scope project

Use --scope project and run it inside each project that should use Forge. This pins the Forge version per project, so upgrading one project never changes another mid-flight.

Why per-project scope matters

A user-scope install is one shared version for everything: update it for a new project and every in-flight project silently jumps versions too — gate behavior can change mid-milestone. Project scope gives each repo its own record. Multiple Forge versions coexist peacefully in the plugin cache; each project loads its own.

3Verify the install

Start a fresh session in the project (claude). You should see the Forge operating contract load at session start. Then run the self-check:

/forge:status

and in any terminal (no AI, no tokens):

node ~/.claude/plugins/cache/forge-marketplace/forge/<version>/bin/forge.js doctor

doctor prints PASS/WARN/FAIL for the whole install: Node and git, which Forge version is actually running, whether the plugin cache is clean, whether hooks parse, and the project's state health. "Install and state look sane" means go.

4Recommended extras (optional)

Graphify — a deterministic code map that makes orientation and scoping nearly free:

uv tool install graphifyy graphify install

Playwright — for web projects, keep it as a dev dependency so end-to-end checks and screen screenshots can be machine-verified. Skipping either is fine: preflight detects what's missing, asks you once, and remembers your answer per project.

Updating Forge later (and why you do it between projects, not during)
  1. Pull/receive the new plugin version in the marketplace repo, then in a session: /plugin marketplace update forge-marketplace
  2. Update the plugin when the UI offers it — or the reliable route when the cache is stubborn: uninstall, clear cache, reinstall: claude plugin uninstall forge rm -rf ~/.claude/plugins/cache/forge-marketplace claude plugin install forge@forge-marketplace --scope project
  3. Run doctor — it flags a cache that's behind the repo and multiple cached versions.

Update at project boundaries (a finished project, or at worst a milestone gate). Never mid-milestone: if behavior then changes, you can't tell whether the new version or the new work caused it.

🌱 Starting a new project

From an idea in your head to a verified product. You talk; Forge structures.

1YOUCreate the project and say what you want

mkdir my-app && cd my-app && git init claude you: "New project — an app where families plan and split holiday budgets."

The spec skill triggers on its own; if it doesn't, say "run the forge method".

2YOUAnswer the interview, one question at a time

Forge walks six layers — Vision → Domain → Experience → API → Logic → Foundation — asking either/or questions with a recommendation each time. You never write spec documents; you answer and approve each layer's gate. Every confirmed choice lands in forge/decisions.md with your authority.

Why an interview instead of "just build it"?

Ambiguity is where AI projects go wrong: the model fills gaps with plausible inventions. The layered interview drains the ambiguity before code exists, when changing course costs a sentence instead of a rewrite. The output is a spec folder that stays the single source of intent for the whole project — and later, the source your user documentation is generated from.

3YOUApprove the milestone cut — and mocks, if your product has screens

Forge proposes milestones: phases that each end in something you can personally try (never "database schema" — always a runnable slice). You confirm or adjust the cut, and choose the gating mode: stop for your testing after each milestone (recommended) or run straight through.

For products with a UI, Forge also offers the drawn frontend: one mock per key screen — made in Claude Design, exported from Figma, or a photographed hand sketch. Approved mocks are stored in spec/mocks/ and become binding: the built screen is verified against them.

What a mock binds (and what it doesn't)

A wireframe-fidelity mock binds intent: what's on the screen, how it's grouped, what the primary action is. It does not bind pixels unless you say so. Screens you decline to mock still get the design-UX checklist at build time (empty/loading/error states, mobile, form rules) — the five states are never optional.

4AUTOThe spec gates — the work graph is born

Forge writes CLAUDE.md and PLAN.md, sets the verification commands, and converts the plan into work items — each with acceptance criteria that carry a machine check (a command that must pass). Preflight runs and reports anything missing.

5YOUSay the word

you: "Build it." (or /forge:build)

The build loop runs — see Daily driving. Walk away whenever you like; everything lives on disk.

6YOUMilestone reviews until done

forge: "Auth + family accounts verified end-to-end. Security pass recorded — no findings. Here's how to try it." you: "Invites should also work by link, not just email."

Your feedback becomes recorded decisions and new work items before you approve the gate — then the next milestone starts. "Done" at the end means every item has a passing verification record; nothing was completed by claim.

🏗️ Working on an existing codebase

From "add this feature" to a baseline-guarded, verified change — without Forge needing to understand your whole system first.

1YOUOpen the repo, ask for the change

cd existing-repo && claude you: "Add CSV export to the reports page."

The brownfield skill triggers (say "use forge-brownfield" if not) and forge init creates the project state.

2AUTOOrientation — scoped to your request only

Forge maps just the affected area (with Graphify when installed, or a cheap explorer agent): entry points, what depends on what, what the change might break. It never reverse-engineers the whole system for a bounded change.

3AUTOBaseline — before any change, no exceptions

Forge finds your project's real test/lint commands (asking you if needed) and runs forge baseline capture: a snapshot of what already passes and what was already broken.

Why the baseline is non-negotiable

It's the difference between "the tests fail" and "the tests fail because of us". Pre-existing failures are recorded as pre-existing: new work must not worsen them and is not blamed for them. From here on, every verification automatically includes the baseline comparison — a regression fails the work item even when its own checks pass. If your project has no runnable checks at all, Forge says so plainly: the first work items build a minimal harness, because unverifiable change is gambling.

4YOUMini-spec — only the questions code can't answer

Forge asks you the product questions for this change (as either/ors) and writes acceptance criteria. Then the same build loop as greenfield runs, with the baseline guard active.

5AUTOThe spec grows as work happens

After each completed change, what it established is merged into a spec folder — so over months, your undocumented codebase converges on the same documented shape as a greenfield project, along the paths where work actually happened.

The provenance tags — intent vs reality

Brownfield specs tag every statement: [CONFIRMED] = you decided it (it's in the decisions log — this is intent). [OBSERVED] = derived from code (this is reality, and it is never silently promoted to intent — if a later change needs it to be intentional, you get asked). _TBD_ = known gap, deliberately open. Contradictions between OBSERVED and CONFIRMED are recorded as discoveries, not silently resolved. Dead corners staying undocumented is honest, not failure.

⚙️ Daily driving — the build loop and your part in it

What runs while you're away, and the few moments that are yours.

Your three interruptions, and how to answer them

Spec holeForge asks an either/or with a recommendation. Just answer in plain language — it's recorded automatically. If you're unsure, ask "what would each option mean for users?" before choosing.
Risk approvalSay yes or no. If no, say what would make it acceptable.
Milestone gateForge tells you how to run the slice. Actually try it — click around, break it. Then: say your verdict and feedback in plain language. Fixes happen before the gate closes. Approval is recorded with forge milestone approve M2 --note "..." (Forge runs it when you give the verdict).
The security pass at every gate. Before the demo, Forge must run a fresh-context security review of everything the milestone changed and record it — the CLI refuses to approve the gate without it. If Forge presents findings, they become fix-items or your explicitly accepted risks; either way it's on the record.

Session habits that keep everything sharp

  • Resume anytime: open claude in the project and say "continue". The session start loads the contract plus a live state digest — no re-explaining, ever.
  • Restart at gates: when a milestone closes, end the session and start a fresh one. Long conversations degrade; the disk doesn't. Forge will suggest this itself.
  • Pause anytime: just say stop. The stop gate makes Forge settle every open item first — done, blocked-with-reason, or failed-with-diagnosis. Nothing dangles silently.
  • New machine or teammate: clone the repo (state travels in git), install the plugin, open claude. Same picture, same rules.
Why fresh sessions beat long ones

A model's attention degrades as a conversation grows — review gets subtly sloppier before it gets visibly wrong. Because Forge keeps all memory on disk, a session is disposable by design: restarting costs ~30 seconds and buys back full sharpness. The rule of thumb enforced by the contract: fresh session at every milestone gate, or whenever the conversation passes roughly a third of the context window.

🛡️ The safety nets

All enforced in code. You'll mostly notice them as things that refuse — that's them working. What each one protects you from:

NetWhat it prevents
Evidence-or-nothingWork marked complete by claim. DONE requires a passing verification record for the current code — edit anything after a green run and it demands a re-verify.
Red-first checksVacuous tests. If every check already passed before work started and nothing changed, completion is refused — a check that can't fail proves nothing.
Retry ladderBurning money on the same mistake. Each failure requires a written diagnosis; the third identical attempt is refused until the approach explicitly changes (stronger model, different decomposition, revised criteria, or do-it-directly).
Milestone gatesBuilding three floors on a cracked foundation. Nothing in milestone N+1 can start until you tested milestone N and approved it — with the security review recorded first.
Baseline guard"The fix broke something else." Every verification compares against the recorded baseline; regressions fail the item automatically.
One orchestratorTwo sessions editing the same project at once (this caused real data loss once). A session lock blocks the second session's writes; a dead session's lock ages out or is cleared with forge session takeover --force.
Scope guardA worker "helpfully" editing files it was told not to touch. Forbidden paths are refused by the hook while the item runs; paths in options.protect (generated code, migrations) are frozen always.
Stop gateSessions ending with work silently half-done. Every open item must be settled — done, blocked-with-reason, or failed-with-diagnosis.
Living specDocumentation drift. Every completed item that touched product behavior updates the spec in the same closing step, on every project — so the spec is always ready to generate user docs from.
Where each net lives (for the curious)

Three hooks fence the session: SessionStart injects the operating contract, a live state digest, and the lock status; PreToolUse guards every file edit (state files, edit-war, scope, protected paths); Stop refuses to end with dangling work. Everything else is refusals inside the CLI itself. The full mechanism diagrams are in docs/architecture.html, and every net has a regression test — the standing rule is that every field failure becomes a permanent test.

🔍 When it says no — every refusal decoded

Refusals are the product working, not breaking. Find the message, read what it means, do the one thing it asks. Type below to filter.

The message says…It meansWhat to do
no acceptance criteriaAn item was started before defining how success is checked.Let Forge write criteria first — this is automatic; you only see it if something was rushed.
unfinished dependenciesThe item depends on work that isn't done.Nothing — the loop picks a ready item instead.
already IN_PROGRESSSomeone tried to start an item that's mid-flight.Resolve it first: done, failed-with-diagnosis, or blocked.
requires --escalateTwo failed attempts recorded; a third identical one is banned.Forge must change approach (stronger model, decompose, revise criteria, or do it directly) and say so explicitly. If you're watching: ask what the diagnosis was.
no passing verification recordCompletion was attempted without evidence.Run the verification. DONE is granted by evidence, not claim.
tree changed since the passing verificationThe code was edited after the green run — the evidence is stale.Re-verify. Takes seconds; keeps evidence honest.
checks … prove nothingEvery check was green before work began and nothing changed — the item was already satisfied or the checks are vacuous. Cancel the item with a reason, or fix the criteria. Never wave it through.
baseline … regressionThe change broke something that worked before it.The item stays failed until the regression is fixed. Deliberate exceptions need --skip-baseline --reason, which is recorded.
milestone … awaits HUMAN approvalThe previous milestone is finished but you haven't reviewed it.This one's yours: try the slice, give your verdict, approve the gate.
no recorded security reviewGate approval attempted before the milestone's security pass.Forge runs the fresh-context security review and records it (forge milestone security M --note). To skip deliberately: --skip-security --reason (logged). Per-project opt-out: options.security off.
state files are managed exclusively by the forge CLISomething tried to hand-edit forge/state/ or forge/config.json. By design — those change only through forge commands, so the audit trail stays true.
EDIT-WAR GUARDA second Claude session tried to write while another session is actively working this project.Close one of the two sessions. If the "other session" is actually dead: forge session takeover --force.
SCOPE GUARDAn edit targeted a file the current work item is forbidden to touch.The worker must stop and report — correct behavior. If the scope itself is wrong, it's revised explicitly with forge task update --forbidden … --reason ….
PROTECTED PATHAn edit targeted a path frozen for the whole project (options.protect — generated code, migrations…).If truly intended, a human changes the protection list first. Otherwise: working as designed.

needs a title — nothing was recordedA decision/discovery was logged without a title.Re-run with a title. Untitled log entries used to lose data silently; now they're refused.
cancelling … dependentsCancelling this item would strand items that depend on it.Decide their fate explicitly: --dependents drop (they proceed without it) or cancel (they go too).

The two debugging instruments

When behavior seems wrong — a refusal that shouldn't fire, state that looks off, anything confusing — the standing rule (for you and for Forge itself) is: diagnose before working around. Both commands are free — no AI, no tokens:

  • forge doctor — the install & state self-check. Catches the boring real causes: an outdated plugin cache, multiple cached versions, corrupt state, a stale session lock, work orphaned by a dead session.
  • forge trace --refusals — the flight recorder. Every command and every hook decision, timestamped and stamped with the Forge version that made it. Filters: --refusals, --hooks, --last 50. Set FORGE_DEBUG=1 before a command to record verbose payloads.
Other things that occasionally happen
  • A skill didn't trigger? Name it: "run the forge method" / "use forge-brownfield".
  • Hooks silent after a Claude Code update? Run /hooks to inspect; reinstall/update the plugin — hook config formats occasionally shift between Claude Code releases. doctor checks the known failure modes.
  • Want different Forge behavior? The process lives in one reviewable file: core/OPERATING.md in the plugin (~150 lines). The design rationale for every rule is in docs/TRACEABILITY.md.

The forge CLI (any terminal — zero tokens)

There is no installed forge binary — the real form is node <plugin-path>/bin/forge.js <command> run from the project root. Inside a Claude session, just say what you want; Forge runs these itself.
