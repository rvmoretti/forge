Forge — how the machine works

Functional view of the plugin: who talks to whom, where the truth lives, and the gates a work item must pass. Companion to manual.html (how to use it) and TRACEABILITY.md (spec → enforcement map).

1 · The one idea

Forge splits an engineering organization across two substrates. Judgment lives in the model: the main session operates as CTO under an operating contract injected at every session start — it runs the spec method, writes briefs, reviews diffs, decides how. Enforcement lives in code: a zero-dependency CLI owns all state transitions and refuses the moves that historically go wrong (unverified DONE, unrecorded retries, skipped gates), and three hooks fence the session itself. The conversation is never the memory — everything recoverable lives in plain files under forge/, so any fresh session resumes from disk.

3 · The life of a work item

Every unit of work — dispatched to a worker or done by the CTO directly — moves through the same state machine. The interesting parts are the refusal edges: transitions the CLI will not perform, whatever the model says.

4 · The two entry flows

Greenfield: spec phase first — the forge-method skill runs the layered interview (vision → domain → experience → API → logic → foundation), the spec gates, milestones are cut as user-testable vertical slices, and the work graph is generated with red-first criteria. Then the build loop of Figure 2, milestone by milestone.

Brownfield: orientation first (Graphify or a haiku explorer maps the affected subsystem), then forge baseline capture — non-negotiable before any change; from then on every verification includes the baseline comparison and a regression fails the item even when its own criteria pass. A mini-spec covers just the requested change, and the spec folder accretes along the paths where work happens, tagged [CONFIRMED] (intent) / [OBSERVED] (reality) / _TBD_ (known gap).

Both flows converge on the same loop, the same state files, and the same living spec — which is what makes the spec usable later as the source for generated user documentation.
